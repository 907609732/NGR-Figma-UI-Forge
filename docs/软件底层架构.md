# NGR Figma UI 锻造台底层架构

本文面向插件开发、排错、代码审查和后续维护人员。普通使用者请阅读[傻瓜式使用教程](./傻瓜式使用教程.md)。

## 1. 系统边界

NGR Figma UI 锻造台由两个可独立构建的部分组成：

1. **Figma 插件**：运行在 Figma Desktop 内，负责读取和修改 Figma 文档。
2. **产品官网**：独立的 React/Vinext 网站，负责介绍、下载和在线教程，不参与插件运行。

插件正式包只需要 `manifest.json`、`code.js`、`ui.html` 和说明文件。源码、Node.js 依赖、测试配置、API 密钥都不属于运行时交付物。

## 2. 工作区目录

```text
Figma UI 锻造台/
├─ manifest.json              # 开发环境 Figma 插件清单
├─ system/
│  ├─ src/code.ts             # Figma 主线程：文档读写、网络请求、配置存储
│  ├─ src/shared.ts           # UI 与主线程共享的类型、默认配置和消息协议
│  ├─ src/ui.html             # 插件界面及浏览器侧交互
│  ├─ scripts/build.mjs       # esbuild 构建入口
│  ├─ tests/                  # 插件自动化测试
│  └─ dist/                   # 开发清单引用的构建结果
├─ website/                   # 官网源代码、资源和渲染测试
├─ docs/                      # 用户教程、交互规则和本架构文档
├─ assets/                    # 品牌源文件
└─ 正式版软件/               # 可复制到其他电脑测试的正式版快照
```

## 3. Figma 双进程模型

Figma 插件不是普通网页。它有两个相互隔离的执行环境。

### 3.1 UI 线程

`system/src/ui.html` 运行在插件 iframe 中，职责包括：

- 渲染命名、模板、功能、变体和设置页面。
- 维护当前表单状态和交互状态。
- 将用户动作转换成消息。
- 展示主线程返回的结果、错误和选区摘要。

UI 不能直接修改 Figma 文档。它通过以下通道发送命令：

```js
parent.postMessage({ pluginMessage: message }, "*")
```

### 3.2 Figma 主线程

`system/src/code.ts` 运行在 Figma 插件主线程中，职责包括：

- 读取 `figma.currentPage.selection`。
- 创建、移动、删除、重命名和组合 Figma 节点。
- 读取和写入 Plugin Data。
- 使用 `figma.clientStorage` 保存设备配置。
- 调用经过 manifest 允许的翻译和 AI 网络接口。
- 把执行结果和错误发回 UI。

主线程通过 `figma.ui.onmessage` 接收命令，通过 `figma.ui.postMessage` 返回结果。

### 3.3 消息协议

消息联合类型集中在 `system/src/shared.ts`，避免 UI 和主线程各自猜测字段。

主要 UI → 主线程消息：

- `SCAN_SELECTION`：重新读取当前选区。
- `APPLY_LEXICON_ENTRY`：应用词库名称及可选属性方案。
- `TRANSLATE_AND_RENAME`：翻译并命名。
- `AUTO_NAME_FRAME`：执行画板整理流水线。
- `ADD_PROGRAM_CONTROL_TO_SELECTION`：给明确多选的节点写程序控制。
- `ADD_TEXT_CONTROL_PROPERTIES`：递归处理选区内文本。
- `CREATE_VARIANTS`：生成 State、Checked、Style 组合变体。
- `INSERT_TEMPLATE`：插入 Library 或内置模板。
- `SAVE_CONFIG` / `IMPORT_CONFIG` / `EXPORT_CONFIG`：配置持久化。

主要主线程 → UI 消息：

- `READY`：初始化配置和选区。
- `SELECTION`：选区变化。
- `RENAME_PREVIEW`：命名预览。
- `APPLY_RESULT`：执行成功摘要。
- `CONFIG_EXPORTED`：序列化配置。
- `ERROR`：可展示的错误信息。

新增功能时，应先扩展共享消息类型，再实现主线程处理，最后接 UI 入口。

## 4. 启动与状态同步

插件启动流程：

```text
manifest.json
  → 加载 system/dist/code.js
  → figma.showUI(system/dist/ui.html)
  → loadConfig()
  → READY(config, selection)
  → UI renderAll()
```

Figma 选区变化会触发 `selectionchange`。主线程重新生成 `SelectionSummary`，再发送 `SELECTION`。UI 中的“刷新”按钮使用相同的扫描逻辑，作为手动纠正入口。

UI 尺寸由主线程限制在宽 `420–900`、高 `520–1000` 的范围内，默认尺寸是 `420 × 820`。

## 5. 配置模型与持久化

`PluginConfig` 是插件配置的单一结构，包含：

- 命名规则和词库。
- 共享属性方案及当前方案。
- 模板列表。
- 百度翻译和可选 AI 配置。
- 画板整理开关。
- 状态层自动切换开关。
- 标准按钮结构开关。

设备配置保存到：

```text
figma.clientStorage["ai-auto-namer-config"]
```

读取旧配置时必须经过 `normalizeConfig()`，用默认值补齐新增字段。这样升级插件后，旧设备上缺少的新开关不会导致启动失败。

项目级配置可以写入当前页面的隐藏配置节点 `.AutoNamePluginConfig`。公开配置导入导出使用 JSON；敏感接口密钥不得提交到仓库或放入正式包。

## 6. 核心业务流水线

### 6.1 命名与属性方案

节点先归类为 `TEXT`、`IMAGE`、`COMPONENT`、`FRAME`、`SHAPE` 或通用 `NODE`，再按 `RenameScope` 解析处理范围：

- `selection`：仅当前选择。
- `children`：直接子级。
- `deep`：递归全部后代。

锁定和隐藏节点是否跳过由 `RenameOptions` 决定。属性方案中的每个字段都有独立开关，未启用的字段不得覆盖节点原值。文本字体相关修改前必须先加载对应字体。

### 6.2 翻译与 AI

百度翻译负责中文到英文的基础命名。OpenAI 兼容接口和 Kimi 属于可选 AI 命名能力。

网络权限由 `manifest.json` 的 `networkAccess.allowedDomains` 限制。新增服务不仅要改 UI 配置，还要同步更新 manifest 白名单、错误处理、隐私说明和测试。

### 6.3 画板整理

画板整理将多个可选步骤串成单次操作：

1. 校验当前选择。
2. 按配置删除隐藏节点和 Mask。
3. 按配置解散 Group。
4. 推导平台类型和规范名称。
5. 可选地写入文本或图片程序属性。
6. 汇总重命名、删除、解散、跳过和属性处理数量。

删除和解散会改变文档结构，因此新规则必须保持默认值明确，并优先在测试副本验证。

### 6.4 程序控制数据

下游程序数据统一写入节点的 Plugin Data：

```text
Key: CMPropertyDataContainer
Value: JSON
  └─ PropertyDatas[]
      ├─ CMVarPropertyData
      ├─ CMTextPropertyData
      ├─ CMImagePropertyData
      └─ CMButtonPropertyData
```

写入规则：

- 新增目标类型前先读取并解析现有容器。
- 已存在相同属性时保持原值，并计入“已存在”。
- 不应覆盖不相关的 Property Data。
- 富文本或滚动数字等冲突类型应跳过普通文本属性。
- 标准按钮结构只给 `HotZone` 补 `CMVarPropertyData` 和 `CMButtonPropertyData`。

普通 Figma Plugin Data 按插件 ID 隔离。当前 manifest ID 与目标项目插件保持一致，是下游能够读取这些字段的前提。

## 7. 一键变体架构

### 7.1 输入模型

`CREATE_VARIANTS` 接收：

- `baseMode`：`style-only`、`three`、`four`、`six`、`eight`。
- `styleMode`：`none`、`complete`、`rank`。
- `applyStateLayerVisibility`：是否按节点名控制状态层。
- `applyButtonStructure`：是否生成 `Content + HotZone`。

基础定义先生成 `State` 与可选 `Checked`，再与 Style 值做笛卡尔组合。

选择按钮中的 `Checked=Checked` 和 `Checked=Unchecked` 是独立于 State 的 Figma 变体属性维度，并驱动名称精确匹配 `Checked` 的视觉节点。`Pressed` 仍只由 State 控制。

### 7.2 状态层显隐

算法递归查找生成组件的全部后代。节点名先去除首尾空格并转为小写，然后只接受五个完整名称：

- `Normal`
- `Hover`
- `Pressed`
- `Disabled`
- `Checked`

`Icon_Normal`、`Icon_Hover`、`Icon_Checked` 等名称不匹配。同名节点可有多个，全部处理。

| State | Normal | Hover | Pressed | Disabled |
|---|---:|---:|---:|---:|
| Normal | 打开 | 关闭 | 关闭 | 关闭 |
| Hover | 打开 | 打开 | 关闭 | 关闭 |
| Pressed | 打开 | 打开 | 打开（存在时） | 关闭 |
| Disabled | 打开 | 关闭 | 关闭 | 打开（存在时） |

State 与 Checked 分别计算后叠加：State 决定 `Hover`、`Pressed`、`Disabled`，Checked 属性决定 `Checked`。因此 `State=Pressed, Checked=Checked` 打开 `Hover + Pressed + Checked`；`State=Pressed, Checked=Unchecked` 打开 `Hover + Pressed` 并关闭 `Checked`。已有 Component Set 追加 Style 时不修改原状态层。

#### 选择按钮完整状态矩阵

根层 `Normal` 状态节点已经接入自动显隐。完整行为如下：

| 变体属性 | Normal | Hover | Pressed | Checked |
|---|---:|---:|---:|---:|
| `State=Pressed, Checked=Checked` | 打开 | 打开 | 打开 | 打开 |
| `State=Pressed, Checked=Unchecked` | 打开 | 打开 | 打开 | 关闭 |
| `State=Hover, Checked=Checked` | 打开 | 打开 | 关闭 | 打开 |
| `State=Hover, Checked=Unchecked` | 打开 | 打开 | 关闭 | 关闭 |
| `State=Normal, Checked=Unchecked` | 打开 | 关闭 | 关闭 | 关闭 |
| `State=Normal, Checked=Checked` | 打开 | 关闭 | 关闭 | 打开 |

该矩阵遵循两个独立维度：

- `Normal` 是所有状态共用的基础层，任何组合下都保持打开。
- State 决定附加状态层。Pressed 保留既有规则，同时打开 `Hover + Pressed`。
- Checked 属性只决定 `Checked`：Checked 打开，Unchecked 关闭。

`StateLayerName` 已包含 `normal`。Normal 与其他状态节点共用递归精确匹配、源组件可见性快照、失败恢复和匹配数量统计，并由 6/8 状态自动化测试覆盖。

### 7.3 标准按钮结构

对新建状态变体，可整理为：

```text
Component
├─ Content
│  └─ 原视觉内容
└─ HotZone
```

`Content` 和 `HotZone` 只复用根层、名称精确匹配且类型为 Frame 的节点，匹配忽略大小写和首尾空格。`HotZone` 必须透明、无描边、覆盖组件全尺寸、横纵 Stretch，并位于根层最上方。

结构处理前会记录源节点、父子关系、布局和 Plugin Data 快照。流程失败时恢复源组件并移除本次创建的节点，避免留下半完成结构。

### 7.4 既有 Component Set

选中既有 Component Set 时，功能只在现有组件基础上追加 Style：

- 不重建 State 或 Checked。
- 不执行状态层自动切换。
- 自动按 Style 值切换同名风格节点，保留各节点原有的 State / Checked 子层显隐。
- 不生成标准按钮结构。
- 已经存在 Style 属性时停止，避免生成重复维度。

### 7.5 Style 同名节点显隐（v0.1.58）

`styleLayerNodes` 递归精确匹配当前风格模式的值：常态和完成模式为 `Normal / Complete`，排名模式为 `1st / 2nd / 3rd`。`applyStyleLayerVisibilityForDefinition` 仅打开与目标 `Style` 值一致的节点，关闭其余匹配到的风格节点；忽略大小写和首尾空格，`Icon_Complete` 不匹配，缺失节点跳过。

Style 自动切换独立于可选的 `applyStateLayerVisibility`，适用于新建、仅 Style 和已有 Component Set 追加。插件不生成另一套设计，源节点必须事先包含所需外观。

`Normal` 同时是 State 基础层名。普通扁平 Normal 保留常显规则；有 State 时，只有与其他风格节点同级、且内部含状态子层的 Normal 容器才作为风格分支。该分支从 State 常显集合中排除，内部 Normal / Hover / Pressed / Disabled / Checked 仍按 State 规则处理。仅 Style 下，同级 Normal / Complete 容器互斥并保留内部状态层原有显隐。

新建和追加前都记录完整后代显隐快照，失败时恢复。回归覆盖三条生成路径、同名冲突、排名、精确匹配和失败恢复；Figma Desktop 已实测四状态乘两种 Style 的 8 组合及仅 Style 的 2 组合。

## 8. 模板系统

模板有两种来源：

- `library`：通过 Figma Library Component Key 导入已发布组件。
- `builtin`：插件在当前文件中创建基础模板骨架。

Library 模板依赖当前 Figma 账号的组件库权限。`detachAfterInsert` 控制导入后是否打散实例。模板失败不能回退成看似成功但结构不同的假结果，应向 UI 返回明确错误。

## 9. 构建流程

插件从 `system/` 目录构建：

```powershell
npm.cmd ci
npm.cmd run typecheck
npm.cmd test
```

`scripts/build.mjs` 使用 esbuild：

- 将 `src/code.ts` 打包为浏览器 IIFE，输出 `dist/code.js`。
- 将版本号和更新日期注入 `src/ui.html`，输出 `dist/ui.html`。
- `--test-config` 输出到 `dist-local`，并生成本机测试 manifest；这些本机配置不进入公开发布物。

官网从 `website/` 目录构建：

```powershell
npm.cmd ci
npm.cmd run lint
npm.cmd test
```

官网测试会先生成服务端构建，再直接请求页面，确认首页和教程的关键内容确实出现在 HTML 中。

## 10. 发布边界

一次完整发布至少包含：

1. 更新源码中的版本和日期。
2. 通过插件类型检查、构建和测试。
3. 生成干净的正式版目录和 ZIP。
4. 审查正式包文件清单，确认没有源码依赖、测试配置或密钥。
5. 校验 ZIP SHA-256。
6. 创建 Git 标签和 GitHub Release，并上传大文件。
7. 同步官网版本、下载地址和教程。
8. 验证公开下载、官网 HTML、HTTPS 和真实 Figma Desktop 导入。

“构建成功”“Release 已创建”和“Figma 中实际可用”是三个不同的验收层级，不能互相替代。

## 11. 修改架构时必须保持的约束

- UI 不直接操作 Figma 文档。
- UI 与主线程消息必须在共享类型中登记。
- 新配置字段必须有默认值和旧配置归一化逻辑。
- 写 Plugin Data 时保留未知和不相关字段。
- 批量功能必须明确是“只处理选择”还是“递归处理后代”。
- 会删除或重排节点的功能必须提供清晰的适用范围和失败恢复。
- 变体名称、排列顺序和显隐规则必须可重复、可测试。
- 新网络服务必须同步 manifest 白名单和隐私说明。
- 正式版目录必须可以独立复制到另一台电脑，不依赖工作区的 `node_modules`。
